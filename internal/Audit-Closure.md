# 2. Что именно сделано

## NX-01 — обе половины правила, а не одна

Аудит рекомендовал два действия и отмечал, что разумно сделать оба. Измерения показали, почему
именно оба: по отдельности каждое оставляет дыру, которую закрывает другое.

**Половина первая — политика.** Новый публичный лимит `MaxDecompressionRatio` (по умолчанию 10 000)
связывает объявленную распакованную длину с доставленными сжатыми байтами. Проверка стоит там, где
уже живут остальные инварианты длин, — в `BinaryFormatHeaderV1.ReadFrom`, до того как появится хоть
один буфер, и только когда сжатие не `None` (при `None` равенство длин уже требуется).

**Половина вторая — конструкция.** `ICompressionAlgorithm` получил инкрементальную перегрузку
распаковки и флаг `SupportsIncrementalDecompression` рядом с ней — ровно тем же способом, каким
`IEncryptionAlgorithm` уже несёт AAD-перегрузки и `AuthenticatesAssociatedData`. Оба встроенных
алгоритма её реализуют. `CompressionService` ведёт их через `PayloadBufferWriter`: арендованный
пробник на 64 КиБ, который вырастает до объявленного размера **один раз** и только тогда, когда
столько данных действительно произведено. Алгоритм без инкрементального пути распаковывается
по-старому и остаётся ограничен первой половиной.

Почему нужны обе:

```text
только политика       кадр, доставивший 8 КиБ мусора и объявивший 40 МБ, проходит проверку
                      соотношения и всё равно аллоцирует 40 МБ  →  измерено 41 063 040 байт

только конструкция    алгоритм без инкрементального пути (любой пользовательский) снова
                      аллоцирует по объявлению

обе                   аллокация ≤ min(MaxPayloadBytes, доставлено × MaxDecompressionRatio),
                      и не больше 64 КиБ, пока payload не произвёл столько же  →  103 016 байт
```

Значение по умолчанию выбрано так, чтобы не отвергать данные, которые честно сжимаются: 10 000
покрывает и теоретический потолок deflate (~1 032:1), и обычные случаи Brotli. Приложение, несущее
сильно повторяющиеся данные, поднимает лимит осознанно — ровно как оно уже поднимает
`MaxArrayLength`.

Попутно закрыт остаток, который аудит отметил в §9: буфер распаковки теперь арендованный и
зануляется при возврате, а не остаётся в куче открытым текстом.

## NX-02 — правило принадлежит движку, а не контейнеру

Решение семантики: **дубликат — это малформед**. Основание записано в §23 и следует из линии §22 на
канонический формат: булево имеет ровно два написания, строка обязана быть валидным UTF-8, и
молчаливое схлопывание дубликата дало бы одному логическому значению неограниченное число
представлений.

Реализация — на границе движка, а не в девяти форматтерах:

- `GraphReader.ReadSequence`/`ReadMap` переводят `ArgumentException` контейнера в
  `BinaryFormatException`, сохраняя причину как `InnerException` по §9. Это покрывает те контейнеры,
  которые отказывают сами;
- после `Complete` движок сверяет материализованное количество с объявленным. Это покрывает те,
  которые молча схлопывают, и не требует от форматтера ничего нового.

Второе опирается на `CountOf`, который до сих пор смотрел только на негенерический `ICollection` и
потому ничего не знал о множествах. Новый `CollectionCountCache` читает счётчик через любой
интерфейс, который тип реализует. Последовательности, допускающие повторы — список, массив,
очередь, — не затронуты: там одно и то же значение дважды это данные, а не дубликат.

## NX-03 и NX-04 — один обход вместо двух дефектов

Аудит для NX-03 рекомендовал отказ. В ходе работы стало видно, что вместе с NX-04 лучше работает
другое решение, и выбрано оно — с явным отступлением от собственной рекомендации, потому что оно
строго лучше по всем трём осям, которые назвал владелец: защита, удобство наследования,
детерминированность плана.

`Candidates` теперь идёт по уровням иерархии, от конкретного типа вверх, с `DeclaredOnly` на каждом
уровне:

- **NX-04 закрыт прямо:** непубличный член базы с `[BinaryInclude]` снова в плане. Рефлексия по
  самому производному типу его не отдаёт — обход по уровням отдаёт;
- **NX-03 закрыт порядком:** ключ сортировки получил третью составляющую — уровень объявления, база
  впереди. План стал полным порядком. Тип без одноимённых членов не сдвинулся ни на байт: третий
  ключ решает только ничью, которой раньше не было чем разрешать;
- **переопределение — один член,** взятый у самого производного объявления, так что атрибуты на
  `override` действуют. Это ровно то, что делала рефлексия раньше, и это сохранено намеренно;
- **сокрытие через `new` — два члена,** и оба ездят. Раньше для свойств выживало одно, а состояние
  базы терялось молча.

Отказ вместо этого лишил бы возможности сериализовать наследника типа, который принадлежит не вам,
и оставил бы NX-04 без ответа. Аргумент аудита против третьего ключа («читатель не отличит два
поля по имени») не состоялся: в позиционном режиме читатель и не смотрит на имена.

## NX-05 — вариант (а), как и выбрал владелец

`BinaryContractAttribute` стал `Inherited = true`. Наследник keyed-типа сам keyed, делит с базой одно
пространство ключей и обязан дать своим членам собственные ключи; неразмеченный член — это
`BinaryTypeException`, называющий его.

Общее пространство ключей — не побочный эффект, а смысл: читатель, у которого есть только база,
пропускает член наследника по объявленной длине, как любой другой незнакомый ключ. Это проверено
тестом: payload, записанный наследником, читается базой.

## NX-06, NX-07, NX-11 — по одной правке каждая

- повторная регистрация видимого id — `BinaryFormatException`, симметрично уже существовавшей
  проверке дубликата keyed-ключа;
- magic и версия читаются `BinaryPrimitives.ReadInt32LittleEndian`;
- `HashSizeInBytes` проверяется один раз, в `ChecksumService`, против диапазона, который способен
  записать заголовок V1, — как уже проверялись `GetMaxCompressedLength` и `GetMaxCiphertextLength`.

## NX-08, NX-09, NX-10 — документация и одно слово

§23 теперь говорит про `DateTime` с `Kind = Local` (момент переживает смену часового пояса,
настенное время — нет) и про дубликаты. Из `<Description>` пакета `ViShap.Viper.Serialization` ушло
«High-performance»: §28 бенчмарк-плана распространяется в том числе на описание пакета, а гейт не
закрыт. Описание теперь перечисляет возможности, которые доказаны тестами, а не скорость, которая не
измерена.

# 3. Что эти правки решили за пределами своего списка

Аудит разделял «текущие исправления» и «будущие возможности». Несколько правок оказались на границе:
они закрывали дефект и одновременно сдвигали пункт из `Audit-Future.md`. Ниже — честный учёт, по
пунктам того документа.

## Сдвинуто существенно

**`Audit-Future.md` §2.3 — инкрементальные декодеры вместо `TryDecompress`.** Предложение было:
«сначала NX-01 как исправление, потом — по цифрам B4 — решать про остальное». Первая половина
сделана: `Deflate` и `Brotli` теперь распаковывают инкрементально, `BrotliDecoder.Decompress` заменил
`TryDecompress`, `DeflateStream` читается порциями. Остались нетронутыми `Deflate.Compress`, который
всё ещё пишет в `MemoryStream` и копирует, и вопрос про `ZLibStream`.

**`Audit-Future.md` §4 — буферно-ориентированный ввод-вывод.** Документ называл отсутствие
`IBufferWriter<byte>` во входных точках фактом, который бенчмарк-план фиксирует (FAIR-07). Теперь
`IBufferWriter<byte>` впервые появился в публичном контракте Viper — в `ICompressionAlgorithm` — и
работает в продакшн-пути. Это не входная точка сериализатора и не закрывает §4. Но это прецедент и
полигон: механика «движок владеет буфером, алгоритм пишет в writer» проверена на реальной фазе, и
Направление B из §8 теперь опирается на существующий пример, а не на чертёж.

**`Audit-Future.md` §5 — генерация исходников.** Документ требовал от будущего генератора
воспроизводить план побайтово и называл замороженные фикстуры арбитром. До правки NX-03 это было
невыполнимо: план зависел от порядка, который рефлексия не гарантирует, и генератор не мог
воспроизвести то, что не определено. Теперь план — полный порядок, выразимый во время компиляции:
`[BinaryOrder]`, ординальное имя, уровень объявления. Обход по уровням иерархии — та же форма,
которую видит генератор, глядя на синтаксическое дерево. Это не шаг генератора, а снятое
предусловие.

**`Audit-Future.md` §7 — сохранение неизвестных полей и эволюция схемы.** Keyed-контракты стали
применимы к иерархиям (NX-05). До этого эволюция схемы обрывалась на первом же наследовании, и
обсуждать «сервис-посредник, читающий и переписывающий сообщение» было рано: такой сервис почти
всегда работает с иерархией типов. Сама функция сохранения неизвестных полей по-прежнему не
существует и остаётся вопросом, завязанным на §16.2.

**`Audit-Refactor.md` §9 — зануление открытого текста.** Документ отмечал, что §13.2 контракта
обещает очистку временных криптобуферов, но открытый текст, которым владеет сериализатор, остаётся в
куче. Буфер распаковки теперь арендуется из пула и возвращается с очисткой, а при любом отказе
зануляется. Это одна из трёх копий, названных в §3.4 `Audit-Future.md`; две другие — `rawPayload` и
`compressed` в `V1FormatPipeline.Write` — на месте.

## Сдвинуто попутно

**`Audit-Future.md` §3.2 — разрешение метаданных на каждый элемент.** Напрямую не тронуто: `Add`
по-прежнему разрешает делегат на каждом элементе. Но `CountOf`, переписанный ради NX-02, убрал
побочную аллокацию на стороне записи: `HashSet<>`, `SortedSet<>`, `FrozenSet<>`, `ImmutableHashSet<>`
и всякий пользовательский `ICollection<T>` раньше не отдавали счётчик через негенерический
`ICollection`, поэтому писались через `Materialize` — промежуточный `List<object?>` со всем
содержимым. Теперь они идут быстрым путём: счётчик, затем перечисление. Байты на проводе те же,
порядок тот же; исчез один список на контейнер. Это пункт из §3.5, где он числился среди
«семантически необходимых» — оказалось, что для множеств он не был необходим.

**Каноничность провода.** NX-02, NX-06 и правило дубликатов вместе убрали три случая, когда один
логический граф имел больше одного корректного представления. Это линия §22 контракта, и она важнее,
чем выглядит: §13.1 вычисляет тег по декодированным полям заголовка, а канонический payload — то, на
что эта гарантия опирается ниже заголовка. Для любой будущей версии формата (§7 `Audit-Future.md`)
канонизация — предусловие, а не украшение.

## Не сдвинуто ничем

Честный список — эти правки к ним не приблизили:

```text
§3.1  боксинг примитивов на обоих направлениях — движок по-прежнему работает в object?
§3.2  разрешение делегата Add на каждом элементе и GetGenericArguments() на каждую запись
§3.3  побайтовая запись и чтение: у ValueWriter по-прежнему нет буфера
§3.4  две из трёх копий конвейера V1 и обе материализации ToArray
§4    Stream остаётся единственной входной точкой; чтение по-прежнему требует seekable
§5    ~100 диагностик IL2xxx/IL3050 на месте; Expression.Compile никуда не делся
§6    адаптеров конкурентов по-прежнему нет, Track B не начат
NX-12 ICompositeFormatter — единственная форма, где дисциплина счётчика держится на соглашении
```

NX-12 оставлен открытым сознательно: у него нет симптома во время выполнения, `ITypeFormatter`
внутренний в v1.0, и тест формы исходников для него относится к набору барьерных тестов, а не к
этим правкам. Он записан в `QA-Plan.md` §30.3 с этим обоснованием.

# 4. Что изменилось для потребителя

Ни одна правка не меняет байты, которые Viper пишет для типа без наследования и без одноимённых
членов; все одиннадцать замороженных фикстур читаются без изменений. Ниже — то, что всё же
изменилось, и что обязано попасть в release note.

**Ломающие изменения раскладки** (затрагивают только типы описанной формы):

- тип, у которого базовый класс объявляет непубличный член с `[BinaryInclude]`, теперь пишет этот
  член. Раньше он терялся, то есть старый payload такого типа неполон по построению;
- тип, скрывающий член базы через `new`, теперь пишет оба члена — сначала базы, затем свой. Раньше
  для свойства выживало одно, а для поля порядок был не определён.

**Сужение того, что читатель принимает** (старые payload, произведённые самим Viper, не затронуты):

- ключ словаря или элемент множества, объявленные дважды, — `BinaryFormatException`. Раньше часть
  контейнеров принимала такой payload, теряя запись;
- `null` как ключ словаря — `BinaryFormatException`;
- повторный идентификатор ссылки — `BinaryFormatException`;
- объявленное расширение при распаковке больше чем в `MaxDecompressionRatio` раз —
  `BinaryLimitException`. Приложение, честно сжимающее сильно повторяющиеся данные, поднимает лимит.

**Расширения публичной поверхности** (совместимы по исходникам):

- `SerializationLimits.MaxDecompressionRatio`;
- `ICompressionAlgorithm.SupportsIncrementalDecompression` и инкрементальная перегрузка
  `Decompress` — обе с реализацией по умолчанию, так что существующая внешняя реализация
  компилируется без изменений и продолжает работать через спан-перегрузку.

**Расширение того, что читатель принимает:**

- наследник `[BinaryContract]`-типа теперь сериализуется. Раньше это было `BinaryTypeException`, то
  есть данных такой формы существовать не может.
