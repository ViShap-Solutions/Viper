# ViShap.Viper — порядок разработки и выпуска

**Статус:** действующий. Утверждён владельцем 2026-09-26.
**Для кого:** для владельца и для любого агента, работающего с репозиторием. Здесь — *как*
работать: ветки, теги, версии, выпуски, замеры, фикстуры. *Что* делает библиотека — в
`System-Contract.md`; что строится сейчас — в `rework/Rework-Plan.md`.

Если этот документ и практика расходятся, неправа практика. Если документ не отвечает на
вопрос — это пробел документа: вопрос решает владелец, и ответ записывается сюда.

# 0. Кратко

```text
main ───────●─────────────────────────────────────●──────────── (v1.0.0)   ●── (v1.0.1)
             \                                   / merge                  / merge
              release/v1.0.0 ──●────●────●──────●──●                     /
                               ↑    ↑    ↑     beta  rc                 /
                   rework/r0 ──┘    │    │                  hotfix/v1.0.1-… (из тега v1.0.0)
                   rework/r1 ───────┘    │
                   test/…, benchmark/… ──┘
```

- **`main`** — последнее выпущенное состояние. Стабильный тег `vX.Y.Z` ставится только на HEAD `main`.
- **`release/vX.Y.0`** — ветка, где собирается следующая версия. Из неё ответвляется вся работа для
  этой версии; в ней ставятся теги `-beta.N` и `-rc.N`.
- **Рабочие ветки** (`rework/`, `feature/`, `bugfix/`, `test/`, `benchmark/`, `docs/`, `ci/`) —
  короткие, от своей `release/`, возвращаются в неё через PR.
- **`hotfix/`** — исправление уже выпущенной версии: от тега на `main`, обратно в `main`, затем
  переносится в открытую `release/`.
- **Версия берётся только из тега.** В `.csproj` номеров версии нет и не будет.
- **Коммиты, слияния и теги делает владелец.** Агент готовит работу в рабочем дереве и сообщение
  коммита.

---

# 1. Принципы

1. **`main` всегда можно выпустить** — и чаще всего он уже выпущен. В `main` не бывает
   недоделанной работы.
2. **Версия проектируется в `release/`, а не в `main`.** Всё, что войдёт в `vX.Y.0`, собирается там.
3. **Одна задача — одна рабочая ветка — один PR.** PR проходит CI; сливает владелец.
4. **Документы меняются вместе с кодом**, в том же PR: контракт, QA-план, бенчмарк-план
   (`CLAUDE.md`).
5. **Опубликованное неизменно.** Отправленный тег не двигают и не удаляют; пакет на NuGet.org
   удалить нельзя, только скрыть.
6. **Совместимость судится по контракту.** Что сломано, а что исправлено, определяет
   `System-Contract.md` (§5 этого документа), а не то, как код вёл себя вчера.

# 2. Ветки

## 2.1 Виды веток

| Ветка | От чего | Куда вливается | Для чего | Skill агента |
|---|---|---|---|---|
| `main` | — | — | Выпущенное состояние; только стабильные теги | — |
| `release/vX.Y.0` | `main` | `main` (один раз, при выпуске) | Сборка следующей minor или major версии; теги `beta`/`rc` | — |
| `rework/<этап>-<суть>` | `release/…` | та же `release/…` | Этап утверждённой переделки (`rework/r1-wire-primitives`) | `viper_refactorer` |
| `feature/<суть>` | `release/…` | та же `release/…` | Новая возможность | — |
| `bugfix/<суть>` | `release/…` | та же `release/…` | Ошибка в ещё не выпущенной работе, в том числе найденная на `beta`/`rc` | — |
| `test/<раздел>` | `release/…` | та же `release/…` | Работа по QA-плану: тесты, чекпойнты | `viper_tester` |
| `benchmark/<суть>` | `release/…` или `main` | туда же, откуда ответвлена | Работа по бенчмарк-плану; сохранение baseline (§6) | `viper_bencher` |
| `audit/<суть>` | `release/…` | та же `release/…` | Независимый аудит; результат — документ в `internal/` | `viper_auditor`, `viper_auditor_next` |
| `docs/<суть>` | `release/…` | та же `release/…` | Только документация | — |
| `ci/<суть>` | `release/…` или `main` | туда же | Только `.github/workflows/` и сборка | — |
| `hotfix/vX.Y.Z-<суть>` | тег `vX.Y.(Z-1)` на `main` | `main` | Исправление выпущенной версии → патч | — |
| `support/vX.x` | последний тег `vX.*` | — (живёт, пока поддерживается) | Патчи старой major-версии после выхода следующей | — |

Правила имён: латиница в нижнем регистре, слова через `-`, одна косая черта. `<суть>` — два-четыре
слова о том, что делается, а не кто делает: `bugfix/keyed-skip-overread`, а не `bugfix/fix2`.

## 2.2 Отвечая на вопрос «так ли принято в enterprise»

Устоявшихся схем три:

| Схема | Как | Кому подходит |
|---|---|---|
| **Git Flow** | Постоянная `develop` для следующей версии, `release/*` только для стабилизации перед выпуском, `hotfix/*` от `main` | Продукты с запланированными версиями; тяжеловесна для одного человека |
| **GitHub Flow** | Только `main` и короткие ветки в неё | Сервисы с непрерывным выпуском; плохо переносит долгие переделки |
| **Trunk-based** | Все коммитят в `main` за флагами | Большие команды с сильной автоматизацией |

Твоя схема — `release/vNext` как ветка, где собирается следующая версия, и всё ответвляется от неё
— это Git Flow, где роль `develop` играет ветка конкретной версии. В enterprise так делают часто
(«release train»). Для библиотеки с версиями и одним владельцем она лучше чистого Git Flow по двум
причинам: ветка сама говорит, какую версию собирает, и после выпуска удаляется, а не живёт вечно.

Две оговорки, которые делают её рабочей:

- **Одна открытая `release/` за раз — правило по умолчанию.** Если параллельно идут `v1.1.0` и
  `v2.0.0`, каждое исправление делается в младшей и **переносится вперёд** слиянием младшей
  `release/` в старшую. Никогда наоборот: `v2` не должна утечь в `v1.1`.
- **Патч выпущенной версии не ждёт следующей `release/`.** Для этого `hotfix/` от тега на `main`
  (§8).

## 2.3 Слияния

- PR сливается **merge-коммитом**, как во всей истории проекта: этапы видны, а теги `beta`/`rc`
  остаются предками `main` после выпуска.
- `release/` → `main` — merge-коммит, без squash и rebase.
- После слияния рабочая ветка удаляется.
- Перед PR рабочая ветка обновляется слиянием своей `release/` в себя, а не rebase: отправленную
  историю не переписывают.

## 2.4 CI

`ci.yml` запускает сборку и весь тестовый проект на PR и push в `main`, `release/**` и
`support/**`. Рабочие ветки проверяются через свой PR. PR с красным CI не сливается.

# 3. Жизненный цикл версии

## 3.1 Шаги

```text
1. открыть     git switch main && git pull
               git switch -c release/v1.1.0 && git push -u origin release/v1.1.0
2. работать    рабочие ветки от release/v1.1.0 → PR в release/v1.1.0
3. alpha       по желанию: функции не готовы, API и формат могут меняться            (§3.2)
4. beta        функции готовы; формат версии заморожен, фикстуры версии добавлены     (§3.2, §7)
5. rc          только исправления; API и формат заморожены; документация готова     (§3.2)
6. выпустить   PR release/v1.1.0 → main, merge-коммит; тег v1.1.0 на HEAD main
7. закрыть     удалить release/v1.1.0; baseline бенчмарков на теге v1.1.0 (§6);
               открыть следующую release/ по необходимости
```

## 3.2 Стадии pre-release

| Стадия | Тег | Что обещает | Что ещё может меняться | Публикуется |
|---|---|---|---|---|
| **alpha** | `vX.Y.Z-alpha.N` | Ничего, кроме «собирается и проходит тесты» | Всё: API, формат, поведение | Только если нужен внешний отзыв. В описании выпуска обязательно: «формат не окончательный — не сохраняйте данные» |
| **beta** | `vX.Y.Z-beta.N` | Все функции версии на месте; **формат заморожен** | API, документация, производительность | Да |
| **rc** | `vX.Y.Z-rc.N` | Кандидат в выпуск: то, что станет `vX.Y.Z`, если ошибок не найдено | Только исправления ошибок | Да |
| **stable** | `vX.Y.Z` | Всё по SemVer (§5) | — | Да |

- Pre-release тег ставится только на коммит ветки `release/…` в origin — CD проверяет это и
  отвергает тег на любой другой ветке.
- `N` начинается с 1 и растёт на каждом следующем теге той же стадии. Стадию нельзя вернуть назад:
  после `rc.1` не бывает `beta.2`.
- Суффиксы — только `alpha`, `beta`, `rc`, через точку с номером. `-preview`, `-rc1`, `-RC.1` CD
  отвергнет: `rc10` сортируется раньше `rc9`, а заглавные буквы — раньше строчных.
- Pre-release версии, которая уже вышла стабильной, не бывает — CD отвергнет `v1.0.0-rc.3` после
  `v1.0.0`.
- Для формата Viper **alpha почти никогда не нужна**: всё, что пишется до заморозки формата, потом
  не прочитается. Сохранять и распространять данные можно, начиная с beta.

## 3.3 Для `v1.0.0` конкретно

```text
ветка                release/v1.0.0 от main (после слияния benchmark/release-v1-closing)
этапы                rework/r0-baseline … rework/r9-release-gate → PR в release/v1.0.0
                     (точные имена — таблица Progress в rework/Rework-Plan.md)
до R6                никаких публикаций: формат ещё меняется
после R6             v1.0.0-beta.N — формат окончательный
после R9             v1.0.0-rc.N   — только исправления
выпуск               release/v1.0.0 → main, тег v1.0.0
```

# 4. Теги

## 4.1 Какие теги бывают

| Тег | Где | Кто и как | Что запускает |
|---|---|---|---|
| `vX.Y.Z` | Ровно HEAD `main` | Владелец, после слияния `release/` или `hotfix/` | CD: тесты, упаковка, NuGet, GitHub Release |
| `vX.Y.Z-alpha.N` / `-beta.N` / `-rc.N` | Коммит на ветке `release/…` в origin — CD проверяет и отвергает любой другой | Владелец | CD: то же, пакет помечен как pre-release |
| локальный (`pre-rework`, `bench-…`) | Любой коммит, только у себя | Кто угодно, **не пушится** | Ничего: имя не начинается с `v`. Нужен харнессу бенчмарков, чтобы записать Baseline (§6) |

## 4.2 Как ставить

```bash
git switch main && git pull                      # или release/vX.Y.0 для pre-release
git tag -a v1.0.0 -m "v1.0.0"                    # аннотированный тег
git push origin v1.0.0
```

## 4.3 Правила

- **Отправленный тег неизменяем.** Не двигать и не удалять. Если CD упал (тесты, упаковка) —
  исправление коммитится, и ставится **следующий** номер: `rc.2` после неудачного `rc.1`; для
  стабильной — патч `vX.Y.(Z+1)`.
- Пакет на NuGet.org **удалить нельзя**, только скрыть (unlist). Поэтому pre-release публикуется
  только тогда, когда он действительно нужен.
- Агент тегов `v*` не ставит никогда. Локальный тег для замера агент может поставить и обязан
  удалить после замера.

# 5. Версии по SemVer 2.0

## 5.1 Три поверхности совместимости

У Viper есть три вещи, которые могут сломаться у потребителя:

```text
API        публичные типы и члены трёх пакетов — исходная и двоичная совместимость
провод     байты, которые пишет и читает библиотека: заголовок V1, payload V0 и V1
поведение  то, что контракт обещает: какие входы принимаются, какое исключение для какого случая,
           лимиты по умолчанию, значения по умолчанию
```

**Мерило — контракт.** Если код расходился с `System-Contract.md`, приведение кода к контракту —
исправление (patch), даже если кто-то полагался на неправильное поведение.

## 5.2 MAJOR — `X.0.0`

Всё, после чего существующий код или существующие данные потребителя могут перестать работать:

| Поверхность | Примеры |
|---|---|
| API | Удаление или переименование публичного типа или члена; изменение сигнатуры; новый обязательный параметр; **новый член интерфейса без реализации по умолчанию** (`I*Algorithm`, `IKeyProvider` — их реализуют потребители); изменение значения публичного `enum`; `class` ↔ `struct`; снятие `virtual`/`sealed`, меняющее наследование |
| Провод | Новая версия не читает то, что писала старая; изменилось кодирование типа, порядок членов, раскладка заголовка, кадр ссылки; изменилась версия формата, которую пишут по умолчанию |
| Поведение | Для того же случая бросается исключение другого типа; **ужесточён лимит по умолчанию** (раньше принималось — теперь нет); изменилось значение по умолчанию любой опции (например, сжатие по умолчанию); отказ от поддерживаемого типа §23; отказ от целевого фреймворка |

Удалять публичное можно только в major, и только если оно было помечено `[Obsolete]` хотя бы в
одной предыдущей minor.

## 5.3 MINOR — `x.Y.0`

Добавление без поломки существующего:

| Поверхность | Примеры |
|---|---|
| API | Новый тип, новая перегрузка, новый метод; член интерфейса **с** реализацией по умолчанию; новый алгоритм (класс и значение `enum`); новый провайдер ключей; `[Obsolete]` на то, что уйдёт в следующей major; новый целевой фреймворк |
| Провод | Новый сервис заголовка (новый номер вида), новый `id` алгоритма. Старый читатель откажет **только** кадру, который их использует, и откажет понятно (`BinaryFormatNotSupportedException`), а кадры без них читает как раньше. По умолчанию ничего нового не пишется |
| Поведение | Поддержка нового типа, который раньше давал `BinaryTypeException`; новая опция с поведением по умолчанию, равным прежнему; **ослабление** лимита по умолчанию (с записью в описании выпуска — это меняет уровень защиты); заметное улучшение производительности |

Нельзя в minor: добавлять необязательный параметр к существующему методу. Это ломает двоичную
совместимость — вместо этого добавляется перегрузка.

## 5.4 PATCH — `x.y.Z`

Никаких новых возможностей:

- исправление ошибки, при котором код начинает делать то, что всегда требовал контракт;
- исправление безопасности — даже если оно отвергает вход, который раньше ошибочно принимался, **при
  условии**, что контракт уже называл такой вход некорректным (так закрывались `HST-40` и `KEY-23`);
- исправление документации, XML-документации, README;
- внутренняя оптимизация без изменения поведения, провода и API.

Если исправление безопасности требует отвергнуть вход, который контракт считал допустимым, это
изменение контракта — minor с явной записью в описании выпуска, а если ломает существующие данные —
major.

## 5.5 Спорные случаи

| Случай | Версия | Почему |
|---|---|---|
| Новый встроенный алгоритм | minor | Используется только по выбору; старые кадры читаются |
| Новый алгоритм по умолчанию | major | Вывод с настройками по умолчанию становится нечитаемым для старых версий |
| Изменение текста сообщения исключения | patch | Контракт гарантирует тип, а не текст |
| Новый тип исключения-наследника для случая, где раньше был базовый | minor | Старый `catch` по-прежнему ловит |
| Исправление, после которого payload, раньше читавшийся с мусором, отвергается | patch | Контракт требовал отказа |
| Генератор исходников (новый пакет, байты те же) | minor | Аддитивно; ни байт, ни существующая сигнатура не меняются |
| Удаление устаревшего `[Obsolete]` | major | Удаление публичного |

## 5.6 Pre-1.0

До `v1.0.0` ничего из этого не действует: формат и API меняются свободно (`rework/Decisions.md`
§1.2). Правила §5 начинают действовать с тега `v1.0.0`.

# 6. Замеры производительности

## 6.1 Виды прогонов

Харнесс сам решает, чем является прогон (`benchmarks/.../Environment/RunTarget.cs`):

| Вид | Условия | Куда пишется | Хранится |
|---|---|---|---|
| **Baseline** | На коммите есть тег; чистое рабочее дерево; полный Track A (`--track A`) без фильтра и без сокращений | `Baselines/<тег>/` | Коммитится навсегда; никогда не переписывается |
| **Partial** | Всё остальное: без тега, с фильтром, сокращённый прогон | `Measurements/` | Не коммитится; в `internal/performance/` цитируется как доказательство, если на нём основано предложение |

## 6.2 Когда делать baseline

```text
каждый стабильный выпуск        на теге vX.Y.Z — обязательный; это «до» для следующей версии
перед большой переделкой        на входном коммите, под локальным тегом (pre-rework) — чтобы каждый
                                этап мог показать, что улучшил
Track B (сравнение с рынком)    после выпуска major или minor, на её теге
```

Pre-release (`beta`, `rc`) — Partial по умолчанию. Baseline на `rc` — только если об этом попросил
владелец.

## 6.3 Как снять baseline и не нарушить порядок веток

Прогон идёт на коммите с тегом, а результат должен попасть в ветку, где идёт работа:

```bash
git worktree add ../viper-bench v1.1.0                    # отдельная копия ровно на теге
cd ../viper-bench
dotnet run --project benchmarks/ViShap.Viper.Serialization.Benchmarks --configuration Release -- --track A
cd -
git switch -c benchmark/v1.1.0-baseline release/v1.2.0    # или main, если release/ не открыта
cp -r ../viper-bench/benchmarks/ViShap.Viper.Serialization.Benchmarks/Baselines/v1.1.0 \
      benchmarks/ViShap.Viper.Serialization.Benchmarks/Baselines/
git worktree remove ../viper-bench
# PR benchmark/v1.1.0-baseline → release/v1.2.0 (или main)
```

Для локального тега (например, `pre-rework`): `git tag pre-rework` → прогон → `git tag -d pre-rework`;
результат коммитится в рабочую ветку этапа.

## 6.4 Правила

- Замер никогда не меняет библиотеку (`viper_bencher`). Предложение по результату — файл в
  `internal/performance/`, решение за владельцем.
- Прилагательное о скорости («fast», «high-performance», «zero-allocation») появляется в README или
  описании пакета только после публикационного gate бенчмарк-плана (§28).

# 7. Формат и замороженные фикстуры

## 7.1 Что это

`tests/.../Fixtures/Wire/*.bin` — байты, записанные выпущенной версией и закреплённые навсегда.
`Format/CompatibilityTests` читает их и сверяет с формами в `Fixtures/Compatibility.cs`. Каждая новая
версия обязана читать все фикстуры всех предыдущих версий той же major.

## 7.2 Когда замораживать

```text
beta версии, которая меняет формат     формат версии заморожен → её новые фикстуры добавляются
                                       в том же PR, что и тег beta.1
только для v1.0.0                      фикстуры перезамораживаются один раз, на этапе R6
                                       (единственное записанное исключение, rework/Rework-Plan.md §0)
```

## 7.3 Как

- **Добавлять, никогда не менять.** Новая возможность формата в minor (сервис, алгоритм) получает
  **новый** файл, названный по версии, которая её ввела: `v1.2-xxhash3.bin`. Существующие файлы не
  трогаются.
- Фикстура создаётся один раз, писателем той версии, которую она закрепляет, и коммитится как байты.
  Тест никогда не создаёт свою фикстуру сам — он бы сверял писатель с самим собой.
- **Упавшая фикстура — это поломка совместимости**, а не фикстура, которую надо обновить. Решение
  одно из двух: исправить код или признать major (§5.2).

# 8. Исправление выпущенной версии

## 8.1 Hotfix → патч

```text
1. git switch -c hotfix/v1.0.1-keyed-overread v1.0.0      от тега
2. исправление + тест-закрепление + контракт/QA-план в том же PR
3. PR hotfix/… → main; CI зелёный; merge
4. тег v1.0.1 на HEAD main
5. перенос вперёд: PR main → открытая release/…  (merge, не cherry-pick)
```

Hotfix не несёт ничего, кроме исправления. Новая возможность «заодно» — это уже minor.

## 8.2 Поддержка старой major

Когда выходит `v2.0.0`, а `v1` ещё нужно чинить:

```text
git switch -c support/v1.x v1.4.2          от последнего тега v1
hotfix/v1.4.3-… от support/v1.x → PR в support/v1.x → тег v1.4.3 на HEAD support/v1.x
```

**Сейчас этот путь закрыт — и так и задумано.** CD принимает стабильный тег только на HEAD `main`, а
`v1.4.3` будет стоять на `support/v1.x`. Открыть его — отдельное решение владельца, которое
принимается тогда, когда появится `v2.0.0` и реальная необходимость чинить `v1`. Варианты на тот
момент:

| Вариант | Что меняется в `cd.yml` | Цена |
|---|---|---|
| a. Не поддерживать старую major | ничего | Пользователи `v1` получают исправления только переходом на `v2` |
| b. Стабильный тег на HEAD `support/vX.x` той же major | стабильный `vX.Y.Z` принимается и на HEAD `origin/support/vX.x`, где `X` — major тега; GitHub Release создаётся с `--latest=false`, чтобы «последней» осталась `v2` | Второй путь выпуска, который надо тестировать |
| c. Выпуск вручную | ничего | Ручной выпуск — ровно то, от чего CD защищает |

До этого решения ветки `support/` не создаются. `ci.yml` уже запускается на `support/**`, так что CI
для них готов заранее.

# 9. Документы в каждом изменении

| Меняется | Что обновить в том же PR |
|---|---|
| Поведение, провод, API | `System-Contract.md` — раздел, который описывает изменённое |
| Тесты | `QA-Plan.md` — чекпойнт с ID и именем теста (`viper_tester`) |
| Замеры | `Benchmark-Plan.md` — чекпойнт и строка результатов (`viper_bencher`) |
| Публичный API | XML-документация для потребителя; `Api/PublicSurfaceTests` сверяет поверхность с контрактом §3 |
| Этап переделки | Записи его change-файла и таблица Progress в `rework/Rework-Plan.md` (`viper_refactorer`) |
| Порядок работы | Этот документ |

**Сообщения коммитов** — на английском, одна строка: что сделано, и, при желании, после тире —
следствие. Без тела, без списка, без трейлера. Подробности — в отчёте и в `internal/`.

**Описание выпуска** на GitHub создаётся CD автоматически из PR. Для major и для minor, ослабляющей
лимит, владелец дописывает раздел «что изменилось для вас».

# 10. Агенты

- Агент работает в рабочей ветке, которую назвал владелец, или предлагает имя по §2.1 и ждёт
  согласия. Он не создаёт и не сливает `release/`, `main`, `support/`.
- Агент **не коммитит, не пушит, не открывает PR и не ставит теги `v*`**. Он оставляет изменения в
  рабочем дереве, перечисляет изменённые файлы и даёт сообщение коммита.
- Skill выбирается по виду ветки (§2.1). Если работа не подходит ни под один вид — это вопрос
  владельцу, а не повод создать новый вид.
- Любой вопрос владельцу — со всеми альтернативами, ценой каждой, коротким примером и
  рекомендацией.
