# 0. Итог

1. **Диагноз в плане верный, и я его проверил по коду.** Две корневые причины — ввод-вывод построен на
   `Stream`, а движок работает с `object` — действительно порождают почти все недавние заплатки:
   требование seekable, `MemoryStream` + `ToArray` на каждом шаге, боксинг каждого `int`, разрастание
   интерфейсов алгоритмов перегрузками. Это не выдумка ИИ.

2. **Главное, что план не говорит прямо: не всё из него обязано случиться до `v1.0.0`.** В релизе
   замораживаются три вещи — байты на проводе, публичный API и публичные интерфейсы (`I*Algorithm`).
   Внутренний движок (`ValueReader`, `GraphWriter`, боксинг, `TypeContract`) — `internal`, и его можно
   переписать в `v1.1` без единого ломающего изменения. План ставит внутреннюю переделку (R1–R4)
   *перед* заморозкой провода (R6), и из-за этого релиз отодвигается на весь объём работы. Можно
   иначе: сначала заморозить внешнее, выпустить `v1.0.0`, потом переделывать нутро. Это главный вопрос
   к тебе (§8, вопрос 1).

3. **V0 «на паритете» (R7) — это расширение твоей просьбы, и в нём есть технические дыры.** Ты просил
   сжатие для V0. План добавил ещё контрольную сумму, шифрование и ссылки. Как это работает без
   метаданных — объяснено в §5.2; там же три проблемы, которых план не видит (Deflate не умеет
   сообщить, где кончились сжатые данные; контрольная сумма проверяется только *после* разбора; у V0
   нет `KeyId`, значит нет ротации ключей).

4. **Extensions в заголовке V1 — правильная и проверенная временем идея** (так устроены PNG, TLS, COSE).
   Объяснение с байтами — §5.1. Но она защищает от устаревания только *заголовок*, а не кодирование
   самих данных — это стоит понимать, прежде чем считать V1 «вечным».

5. **Генератор, собирающий `TypeContract` при компиляции, — это не «быстрее конкурентов».** Это схема
   System.Text.Json в режиме метаданных: убирает рефлексию, холодный старт и открывает NativeAOT, но
   на горячем пути уступает MemoryPack, который генерирует весь код сериализации. План выбрал это
   сознательно — ради того, чтобы учёт лимитов оставался в одном месте. Есть промежуточный вариант,
   который стоит заложить уже сейчас (§5.3).

6. **R0 не требует тега.** Тег нужен только потому, что бенчмарк-харнесс называет «baseline» лишь
   прогон на теговом коммите. Прогон на нетеговом коммите он сохраняет как `Partial` под SHA — для
   сравнения «до/после» внутри рефакторинга этого достаточно (§4.6).

7. **Найдено в проверке:** одно расхождение кода с принципом канонического провода (неминимальные
   7-битные целые принимаются уже сегодня), несостыковка D-3 с правилом «фикстуры перезамораживаются
   один раз», коллизии ID в `Benchmark-Plan-Changes.md`, «одиннадцать фикстур» вместо тринадцати,
   несколько неточностей в `Audit-Future.md`. Полный список — §3 и §4.

# 1. Что вообще предлагается — простыми словами

## 1.1 Корневая причина первая: всё построено на `Stream`

`ValueReader`/`ValueWriter` — единственные классы, которые трогают байты (это «монополия на байты»,
хорошее решение первого рефакторинга). Но внутри у них `Stream`. У `Stream` три свойства, которые
тянут за собой всё остальное:

- **Его нельзя «подсмотреть».** Чтобы понять, V1 это или V0, `FormatRouter` читает 8 байт и
  отматывает позицию назад. Отмотать можно только seekable-поток. Поэтому *любое* чтение сегодня
  требует seekable (`FormatRouter.cs:22`), и `NetworkStream` не читается вообще.
- **В него нельзя вернуться и дописать.** Keyed-поле пишется так: ключ, 4 байта длины-заглушки, само
  поле, потом возврат назад и запись настоящей длины (`GraphWriter.cs:264-281`). Возврат —
  это `Stream.Position = ...`, то есть снова seekable. V1 это прячет, потому что пишет payload в
  `MemoryStream`; V0 пишет прямо в поток пользователя — отсюда `NotSupportedException`.
- **Каждый байт — виртуальный вызов.** `WriteBoolean` делает `stackalloc` на 1 байт и зовёт
  `Stream.Write`, который проходит через `MeteredWriteStream` в `MemoryStream`. Флаг null есть у каждого
  значения ссылочного типа, так что это самая частая операция библиотеки.

Отсюда же копии. Простейший `Serialize<T>(T)` без сжатия и шифрования сегодня делает: `MemoryStream`
для payload → `ToArray` → ещё `MemoryStream` для всего кадра → `ToArray`, плюс `MemoryStream` для
associated data, который строится **даже без шифрования** (`V1FormatPipeline.cs:42`). Со сжатием и
шифрованием добавляются ещё два `ToArray` (`CompressionService.cs:50`, `EncryptionService.cs:65`). Для
payload в 50 МБ это несколько лишних копий по 50 МБ в Large Object Heap.

**Что предлагает план:** заменить `Stream` внутри на буферы. `WireWriter` пишет в собственный
пул-буфер сериализатора (`PayloadBuffer`), где можно вернуться и дописать длину; `WireReader` читает из
`ReadOnlySequence<byte>`/`ReadOnlySpan<byte>`, которые знают свою длину и которые можно подсмотреть
без отмотки. `Stream` становится адаптером снаружи: при записи в него копируются готовые байты, при
чтении из него сначала набирается один кадр.

## 1.2 Корневая причина вторая: движок работает с `object`

```csharp
IScalarFormatter.Write(ValueWriter writer, object value, Type declaredType)   // int → object: бокс
object IScalarFormatter.Read(ValueReader reader, Type declaredType)           // int → object: бокс
MemberBinding.Get : Func<object, object?>                                     // каждое поле — бокс
```

«Боксинг» — это когда `int` (4 байта на стеке) заворачивается в объект в куче (24 байта + работа GC).
`int[]` на миллион элементов сегодня создаёт миллион мусорных объектов при записи и ещё миллион при
чтении. Каждое примитивное поле каждого объекта — тоже.

Плюс «долг реализации», который я нашёл в коде именно там, где его описывает `Audit-Future.md` §3.2:
`HashSetFormatter.Add` на **каждом** элементе вызывает `ElementType(declaredType)` →
`GetGenericArguments()` (новый массив `Type[]`) и ищет делегат в словаре
(`SequenceFormatters.cs:103`). `ConcreteMapFormatter.Add` делает то же на каждой записи словаря
(`MapFormatters.cs:66-71`).

**Что предлагает план:** `IFormatter<T>` вместо `IScalarFormatter`. `Write(ref WireWriter, in T, ref
OperationState)` — никакого `object`, никакого бокса. Форматтер для `T` лежит в статическом
`FormatterCache<T>.Instance` — это трюк .NET: у каждого закрытого generic-типа свои статические поля,
так что поиск форматтера превращается в чтение одного поля, без словаря. `object` остаётся только там,
где тип действительно неизвестен до выполнения: `[BinaryUnion]`, интерфейс, `object`.

## 1.3 Почему «сейчас»

Пока нет ни одного опубликованного пакета и ни одного чужого payload, изменить провод стоит только
работы. После `v1.0.0` каждое изменение провода — это новая версия формата или совместимость навсегда.
Это правда. Но — см. §2 — правда только для провода и публичной поверхности.

# 2. Что на самом деле замораживается в `v1.0.0`

Это то, чего нет в плане явно, и то, что, по-моему, важнее всего для твоего решения.

| Что | Замораживается релизом? | Этапы плана |
|---|---|---|
| Байты на проводе (V1, V0, keyed, ссылки, заголовок) | **Да, навсегда** | R6, R7 |
| Публичный API `BinarySerializer`, опции, `StreamExtensions` | **Да** (удалить потом = ломающее изменение) | R3, D-6, D-8 |
| Публичные интерфейсы `ICompressionAlgorithm`, `IChecksumAlgorithm`, `IEncryptionAlgorithm` | **Да** — их реализуют чужие люди | R5 |
| `ValueReader`/`ValueWriter` → `WireReader`/`WireWriter` | Нет, `internal` | R1 |
| `MemoryStream` и копии в пайплайне | Нет, `internal` | R2 |
| Типизированный движок, боксинг, `FormatterCache<T>` | Нет, `internal` | R4 |
| Основа для генератора (внутренний контракт плана объекта) | Нет, `internal` | R8 |
| Аннотации AOT | Добавляются в любой момент | R8 |

Утверждение плана §2.4 «после `v1.0.0` каждый пункт стоит версии формата» верно для строк с «Да» и
неверно для строк с «Нет». R1, R2, R4 и почти весь R8 — внутренние: сегодня `ITypeFormatter`
специально `internal`, чтобы его можно было менять.

Отсюда два возможных порядка — **я не выбираю, это вопрос 1 в §8**:

```text
Порядок плана (нутро → провод → релиз)
  R0 замер · R1 буферы · R2 пайплайн · R3 входы · R4 типизированный движок · R5 алгоритмы
  · R6 провод · R7 V0 · R8 основа генератора · R9 релиз
  + релиз выходит уже быстрым; бенчмарки v1.0.0 сразу хорошие
  + внутренние этапы проверяются старыми фикстурами, провод не может «уплыть» случайно
  − релиз ждёт всю работу; R4 — самый большой и рискованный этап — стоит перед релизом

Порядок «сначала внешнее» (провод и поверхность → релиз → нутро)
  провод (W1–W3, W6, минимальные varint) на текущем движке · интерфейсы алгоритмов (R5)
  · форма публичного API (R3, новые входы пока как адаптеры) · решения по V0 → v1.0.0
  → затем R1, R2, R4, R8 в v1.x, измеряя против тега v1.0.0
  + заморожено ровно то, что замораживается; дальше можно без спешки
  + Benchmark-Plan уже устроен вокруг тега v1.0.0 — R0 и «pre-rework» становятся не нужны
  + изменения провода на текущем коде небольшие (см. §4.3 — keyed вообще не меняется)
  − v1.0.0 выходит медленнее, чем мог бы; буферные входы сначала работают через адаптер
  − если внутренняя переделка потом покажет, что публичная форма неудачна, чинить уже под совместимостью
```

Промежуточный вариант тоже возможен: провод и поверхность первыми, но релиз всё равно после R4.
Тогда внутренние этапы проверяются уже *новыми* фикстурами, и специальный «оракул» R0 не нужен.

# 4. Проверка `Rework-Plan.md` и файлов изменений

## 4.1 Что в плане сделано хорошо (проверено)

- **Он поправил твой диагноз, и поправил верно.** Ссылкам seek никогда не был нужен. Seekable нужен
  keyed-контрактам (патч длины) и чтению (подсмотр версии). Код это подтверждает.
- **Отказ от неявных id ссылок (W3) — правильная и неочевидная мысль.** Если бы читатель сам
  присваивал `next++`, то, пропустив неизвестное keyed-поле, он не присвоил бы id объектам внутри, и
  счётчики писателя и читателя разошлись бы. Явные id — цена совместимости `PreserveReferences` с
  эволюцией схемы.
- **Фиксированный `int32` длины keyed-поля (W4) — правильно.** Длина неизвестна, пока поле не записано.
  Если бы она была varint, пришлось бы либо писать её неминимально (ломает канонический провод), либо
  сдвигать байты поля после записи — это O(размер) на каждый уровень вложенности, квадратично по
  глубине.
- **Проверены факты про BCL:** Zstandard нет в `net10.0`; у AES-GCM нет инкрементального API;
  `ChaCha20Poly1305.IsSupported` есть; HKDF есть; в `System.IO.Hashing` есть `Crc64`, `XxHash64`,
  `XxHash3`, `XxHash128`. Размер нынешнего заголовка V1 — действительно 29 байт.
- **Инварианты INV-1…INV-13 перечислены полно**, и правило «если этап требует ослабить инвариант —
  стоп и вопрос владельцу» — ровно то, что защищает тебя от решений ИИ, которые тебе не понравятся.

## 4.2 Найденные проблемы

**P1. Неминимальные 7-битные целые принимаются уже сегодня.** *Закрыт 2026-09-26: вариант b, строгое чтение, HST-40.* `ValueReader.Read7BitEncodedInt` читает
`0x85 0x00` как 5 — так же, как `0x05`. Тесты проверяют «слишком много байт» и «больше `Int32`», но
не «лишний байт». Контракт §22.1 объясняет, почему `bool` и UTF-8 обязаны быть каноническими: AEAD
считает тег по *декодированным* полям заголовка, и два разных написания одного значения дают один тег.
С длинами строк заголовка (`KeyId`, имена custom-алгоритмов) сейчас ровно та же ситуация: байты кадра
можно изменить, не сломав тег. Смысл при этом не меняется, так что это не дыра в безопасности, а
расхождение с заявленным принципом канонического провода. План закрывает это в R6 («minimal encoding
only»), но в §1 «State at entry» пишет, что код и контракт синхронны — формально контракт минимальность
не обещает, по духу — обещает. Решать тебе: чинить сейчас отдельно или в составе провода.

**P2. D-3 противоречит правилу «фикстуры перезамораживаются один раз».** Битовая маска null (W5)
откладывается «до данных Track A после R6». Но после R6 провод уже заморожен. Значит, либо маска
приходит до релиза — и фикстуры перезамораживаются второй раз, — либо после — и это новая версия
формата или extension. Надо решить до R6, а не после.

**P3. «Сжатые потоки самоограничены» — не для Deflate в BCL.** План (§7) говорит, что сжатый V0 не
требует внешней длины, потому что декодер сам знает, где конец. `BrotliDecoder` действительно сообщает,
сколько байт он поглотил. А у `DeflateStream` нет способа узнать, сколько входа осталось
непрочитанным: он читает источник блоками вперёд. Значит, V0 + Deflate, встроенный в более длинный
поток, невозможно корректно остановить средствами BCL. Практический вывод: V0 с *любой* фазой требует
ограниченного источника (точный span, sequence или явная длина). Это проще сформулировать одним
правилом, чем делить по алгоритмам.

**P4. Контрольная сумма V0 проверяется после разбора.** В V1 сумма проверяется над сырым payload
*до* построения графа (`V1FormatPipeline.cs:156`). V0-трейлер стоит после payload, а где payload
кончается, известно только после декодирования. Значит, граф строится из непроверенных байт, и
повреждение проявится как `BinaryFormatException` или мусор, а не как `BinaryIntegrityException`.
Лимиты при этом работают, так что это не дыра, но семантика отличается от V1, и план этого не называет.

**P5. У V0 нет `KeyId`.** Шифрование V0 с пустыми associated data работает только с одним заранее
согласованным ключом. Ротации ключей нет. Для IPC это нормально, но должно быть написано.

**P6. Судьба «V0 внутри более длинного потока».** Сегодня V0 можно читать из потока, где после него
идут другие данные (§22.8, тест V0-24). План переводит потоки в адаптеры, которые набирают «кадр» — но
у V0 нет кадра. Для seekable-потока можно прочитать вперёд и отмотать к концу корня; для
non-seekable — только с внешней длиной. План этого не проговаривает, а это поведение сегодня
закреплено тестом.

**P7. Цель «0 байт» на записи не учитывает обнаружение циклов.** `GraphWriter` на каждую операцию без
`PreserveReferences` создаёт `HashSet<object>` (`GraphWriter.cs:22`). Пока он не пулится (или не
заменён чем-то без аллокации), цель §11 «`Serialize` в `IBufferWriter` — 0 байт» недостижима.
Плюс associated data сегодня строятся через `MemoryStream` + `BinaryWriter`. Оба решаемы, но их нет в
списке.

**P8. Коллизии ID в `Benchmark-Plan-Changes.md`.** Файл предлагает «новые» `MICRO-13` и `MICRO-14`, а в
`Benchmark-Plan.md` они уже заняты (грант `InternalsVisibleTo`, строки 588–589). Предлагаемый «новый»
`WL-15` тоже уже существует («Read a payload whose schema differs»). Правило «продолжать с
наибольшего номера» здесь нарушено. В `QA-Plan-Changes.md` все ID проверены — коллизий нет, и все
цитируемые тестовые файлы существуют.

**P9. «Одиннадцать фикстур»** — их 13 (см. §3).

**P10. D-2 (отпечаток схемы) сложнее, чем выглядит, и не обязан блокировать R6.** «Хэш плана членов»
надо определить: входят ли имена CLR-типов (тогда переименование класса ломает отпечаток, хотя провод
совместим)? Вложенные типы? Generic-аргументы? Для keyed-контрактов отпечаток противоречит самой идее
эволюции схемы, значит только позиционные. И главное: если extensions работают, отпечаток можно
добавить в v1.x как extension — ровно для этого они и нужны. Рекомендация «да, в R6» не следует из
собственной логики плана.

**P11. Отпечаток как *критическое* расширение — спорно.** Критическое значит «старый читатель,
не знающий его, отказывается читать». Но отпечаток — это дополнительная проверка, а не изменение
смысла данных; старый читатель мог бы безопасно его игнорировать. Критичность имеет смысл, только если
ты хочешь, чтобы писатель мог *принудить* читателя к проверке.

**P12. Associated data можно упростить.** Сегодня AAD — отдельный «образ» полей, собираемый заново.
`OnDiskLength` исключён, потому что известен только после шифрования. Но план вводит
`IEncryptionAlgorithm.Overhead` — с ним длина шифротекста известна *до* шифрования (для AES-GCM это
длина + 28). Тогда AAD может быть просто байтами заголовка как они лежат на проводе, целиком. Так
делает COSE (стандарт подписанных/зашифрованных контейнеров): «защищённый заголовок как есть». Это
убирает целый класс вопросов о каноничности — нечего сравнивать, байты те же.

**P13. Zstandard может появиться в .NET 11.** По моим сведениям, в `System.IO.Compression` для .NET 11
был одобрен Zstandard; проверь на дату решения. Если так, D-4 меняется: Zstd можно будет добавить как
встроенный без нативной зависимости — но только при переходе на `net11.0`.

## 4.3 Что реально меняется на проводе (W1–W12) — в сравнении с сегодняшним

| Элемент | Сегодня | После R6 | Экономия |
|---|---|---|---|
| Счётчик коллекции | `int32`, 4 байта | varint, 1 байт до 127 | 3 байта на коллекцию |
| Кадр ссылки | маркер 1 байт + `int32` = 5 байт | один varint `(id << 1) \| back` — 1 байт для первых 64 id | 4 байта на каждый ссылочный объект |
| Keyed-поле | 7-bit ключ + `int32` длина | varint ключ + `int32` длина | **ничего — это то же самое** |
| Строка, блоб | 7-bit длина | varint длина | ничего, кроме правила минимальности |
| Флаг null | 1 байт | 1 байт | — |
| Тег union | 1 байт | 1 байт | — |
| Заголовок V1 без фаз | 29 байт | около 7–10 | ~20 байт на кадр |
| Примитивы (`int`, `double`…) | фиксированная ширина | фиксированная ширина | — |

«Varint» (LEB128) — число пишется по 7 бит в байт, старший бит байта говорит «будет ещё байт». 5 — это
`0x05` (1 байт), 300 — `0xAC 0x02` (2 байта). «Минимальная кодировка» — запрет писать 5 как
`0x85 0x00`.

Итого: провод меняется умеренно, и все эти изменения реализуемы на **текущем** движке за
`ValueWriter.WriteCount` и `GraphWriter.WriteStructural`. Это аргумент в пользу порядка «сначала
внешнее» из §2.

## 4.5 Типизированный движок — что план недоговаривает

- `WireReader`/`WireWriter` как `ref struct` нельзя хранить в полях обычных классов. Значит
  `GraphReader`/`GraphWriter` тоже станут `ref struct` или набором статических generic-методов — это
  перестройка всего движка, а не замена типа. MessagePack-CSharp устроен именно так
  (`ref MessagePackWriter`), так что это проверенный путь, но объём честно больше, чем «R4» в одну
  строку.
- Каждое закрытие generic-типа над value-типом (`MemberBinding<Person, int>`, `ListShape<List<int>, int>`)
  JIT компилирует отдельно. Холодный старт вырастет; план это называет риском, и правильно.
- «Движок владеет каждым циклом» (INV-5) касается циклов по *данным с провода*, то есть чтения. На
  записи перечисление коллекции без бокса энумератора требует типизированного кода на каждую форму —
  это нормально, но должно быть явно разрешено в контракте, чтобы не выглядело нарушением INV-5.

## 4.6 R0 без тегов

Тег в R0 нужен по одной причине: `RunTarget.Decide` (`benchmarks/.../Environment/RunTarget.cs:44`)
называет прогон `Baseline` только если `git describe --exact-match` находит тег. Без тега тот же полный
прогон сохраняется как `Partial` под `git describe --always` (то есть под SHA) и помечается как «не
baseline». Для сравнения «до/после» внутри рефакторинга это ровно то, что нужно: цифры есть, и никто не
примет их за опубликованные.

Варианты, без тега:

```text
A. Полный прогон Track A на текущем коммите как Partial; SHA записывается в плане как «точка до».
B. Ничего не мерить до рефакторинга — только при порядке «сначала внешнее» (§2), где точкой отсчёта
   становится тег v1.0.0, как Benchmark-Plan и задумывал.
C. Локальный тег, который не пушится (CD срабатывает только на v* в origin) — ты сказал, что не хочешь;
   упоминаю только для полноты.
```

«Оракул» R0 (запись байтов всех семейств типов) — по сути расширенный набор фикстур на время
рефакторинга. Дешевле — не .bin-файлы, а тест, сравнивающий SHA-256 от вывода по всему корпусу с
записанным списком хэшей. Та же сила, один файл, удаляется в R6.

# 5. Объяснение механизмов

## 5.1 Extensions в заголовке V1 — что это и как работает

**Проблема.** Сегодня заголовок — жёсткая последовательность полей. Захочешь в v1.3 добавить новое
поле — старый читатель v1.0 его не ожидает и прочитает следующие байты неправильно. Остаётся только
новая версия формата (V2), и все старые читатели перестают понимать новые кадры.

**Решение — список «тег–длина–байты» в конце заголовка.** Читатель, увидев незнакомый тег, знает
длину и может его перепрыгнуть. Остаётся вопрос: *можно ли* его перепрыгнуть? Если расширение
говорит «payload зашифрован по-новому», то старый читатель, перепрыгнув его, прочтёт мусор. Поэтому у
тега есть **бит критичности**:

```text
extensions:  varint count
             для каждого: varint tag · varint length · length байт

tag = (номер << 1) | critical

незнакомый, critical = 0  → пропустить по длине, читать дальше
незнакомый, critical = 1  → отказать: BinaryFormatNotSupportedException
все extensions входят в associated data → подменить или удалить их нельзя, не сломав тег
```

Пример. В v1.2 ты добавляешь «метку времени создания» (некритично, tag = 2·1+0 = `0x02`) и «новый
режим кодирования строк» (критично, tag = 2·2+1 = `0x05`). Кадр с меткой времени читается v1.0 без
проблем — метка просто игнорируется. Кадр с новым режимом строк v1.0 отклоняет с понятной ошибкой,
вместо того чтобы молча прочитать мусор.

**Где это уже работает.** PNG: регистр первой буквы имени чанка говорит, критичен ли он (`IHDR`
критичен, `tEXt` нет). TLS: расширения в ClientHello. COSE/JOSE (стандарты подписанных и
зашифрованных контейнеров): параметр `crit`. Это одна из самых проверенных идей в форматах данных.

**Чего extensions не решают — важно.** Они расширяют *заголовок*. Если ты захочешь изменить, как
кодируется `DateTime` внутри payload, extension может только *объявить* «здесь новое кодирование»
(критично) — старые читатели такой кадр прочитать не смогут. То есть extensions дают *управляемое*
устаревание вместо внезапного, но не бессмертие. Настоящая «вечность» V1 держится на том, насколько
хорошо payload-кодирование продумано сейчас.

## 5.2 V0 с фазами — как сжатие, сумма и шифрование работают без метаданных

**Идея.** V1 записывает в заголовок «я сжат Brotli, зашифрован AES-GCM». V0 не записывает ничего — но
обе стороны настроены одинаково (это и есть исходная посылка V0). Значит, читатель *знает* из своей
конфигурации, что применять:

```text
V0 без фаз        [payload]
+ сжатие          [сжатый payload]                        — читатель распаковывает, потому что так настроен
+ контр. сумма    [payload][сумма N байт]                  — N известно из алгоритма
+ шифрование      [nonce 12][шифротекст][тег 16]           — associated data пустые
```

**Сильная сторона, которую план верно замечает.** В V1 злоумышленник может подсунуть незашифрованный
кадр, и спасает только политика `RequireEncryption`. В V0 читатель *всегда* расшифровывает, потому что
так настроен, — незашифрованный кадр просто не пройдёт проверку тега. Даунгрейд невозможен
конструктивно.

**Слабые стороны, которые план не называет** (подробно — P3–P6):

- с любой фазой нужен точно ограниченный источник — Deflate в BCL не умеет сказать, где кончился;
- сумма проверяется после разбора, а не до;
- нет `KeyId`, нет ротации ключей;
- поведение «V0 внутри более длинного потока» надо переопределить.

**Твоя исходная идея и что с ней стало.** Ты предложил «сжатие внутри payload». `Audit-Future.md` §7
понял это как *посполевое* сжатие: keyed-поле несёт признак «я сжато» в своих байтах. План вместо
этого сделал сжатие *всего* payload из конфигурации. Это разные вещи:

```text
посполевое (Audit-Future §7)   сжимается одно большое поле; признак в самом поле; работает и в V0,
                               и в V1; новое правило провода; бомба декомпрессии на уровне поля
весь payload (план, R7)        как в V1, только без заголовка; проще; требует ограниченного источника
```

А контрольная сумма, шифрование и ссылки для V0 — это то, что ИИ добавил сам, развив аргумент «обе
стороны и так настроены вместе». Аргумент логичен. Цена: каждая фаза существует в двух обвязках (V1
и V0), удваивается набор тестов, и V0 перестаёт быть «голым payload, которое понятно с одного взгляда».
Выигрыш против V1 после R6: примерно 7–10 байт заголовка на сообщение.

**Моё мнение**, раз ты спрашиваешь «что с этим делать»: самый честный вопрос здесь — *для кого V0*. Если
V0 — это «IPC, где канал уже защищён и обрамлён», то ему не нужны ни сумма, ни шифрование (их даёт
канал), а сжатие — полезно. Если V0 — это «V1 без 10 байт», то паритет оправдан, но тогда стоит
спросить, не проще ли сделать заголовок V1 ещё компактнее. Вопрос 3 в §8.

## 5.3 Генератор исходников и `TypeContract` при компиляции — быстро ли это?

**Как сегодня.** При первой встрече с типом `TypeContractCache.Build` через рефлексию находит члены,
сортирует их, проверяет атрибуты и компилирует делегаты `Expression.Compile()` для чтения и записи
каждого члена. Это делается один раз на тип и кэшируется.

**Что даст генератор по плану.** То же самое, но при компиляции: генератор видит `[BinaryContract]`,
строит план членов и выписывает C#-код со списком членов и делегатами доступа. Что это даёт:

```text
холодный старт        нет рефлексии и Expression.Compile при первом вызове — заметно быстрее
NativeAOT и trimming  становятся возможны: нет динамического кода
ошибки атрибутов      видны в IDE при компиляции, а не при первом Serialize
горячий путь          почти не меняется: всё равно вызов делегата на каждый член
```

**Лучше ли это конкурентов? Нет — и это не цель.** Это ровно режим «метаданных» System.Text.Json
(`JsonTypeInfo`). Быстрее всех на горячем пути MemoryPack: его генератор пишет *весь* метод
сериализации — прямые `writer.WriteInt32(value.Age)` подряд, без делегатов, и JIT может всё
заинлайнить. Генератор только метаданных так не умеет.

**Почему план сознательно не пошёл путём MemoryPack.** Если генератор пишет весь код, он пишет и
проверки — глубину, бюджеты, длины. Это «второй сериализатор»: второе место, где можно забыть лимит.
Первый рефакторинг потратил много сил, чтобы учёт жил ровно в одном месте (INV-5). Это настоящая
ценность Viper, и план её бережёт.

**Промежуточный вариант, который стоит заложить в R8** (моё предложение, в плане его нет). Пусть
внутренний «план объекта» будет не только *данными* (список членов), а *методом*:

```csharp
// внутренний контракт; рефлексия реализует его циклом, генератор — прямым кодом
interface IObjectPlan<T>
{
    void WriteMembers(ref WireWriter writer, in T value, ref Engine engine);
    void ReadMembers(ref WireReader reader, ref T value, ref Engine engine);
}

// сгенерированный код — только порядок и доступ, никаких лимитов:
engine.Write(ref writer, value.Name);
engine.Write(ref writer, value.Age);
```

Каждое `engine.Write` — это движок, который учитывает глубину, бюджет и ссылки как и раньше.
Генератор решает только «какие члены и в каком порядке», и ни одной проверки не пишет. Горячий путь
становится прямым кодом без делегатов, а безопасность остаётся в одном месте. Если заложить форму
`IObjectPlan<T>` сейчас, генератор потом сможет выбрать любой из двух вариантов; если заложить только
«список членов», путь к прямому коду закрыт до следующей переделки.

Ближайший аналог этой идеи — PolyType + Nerdbank.MessagePack (см. §6): генератор описывает «форму»
типа, а сериализатор поверх неё отдельный.

## 5.4 Буферы и владение — почему одна копия неизбежна

V1 пишет в заголовке длину payload после всех фаз. Эта длина известна только когда фазы отработали.
Значит, payload надо сначала собрать где-то у себя, а потом написать заголовок и скопировать. Нельзя
зарезервировать место под заголовок в чужом `IBufferWriter` и вернуться: интерфейс не обещает, что
выданный ранее кусок памяти ещё твой (ловушка, которую верно заметил `Audit-Future.md` §4).

Поэтому план пишет в собственный `PayloadBuffer` (сегменты из `ArrayPool`), в нём же патчит длины
keyed-полей, и в конце копирует один раз в назначение. Одна копия, из пула, с очисткой. Сегодня копий
от двух до четырёх, и они не из пула.

## 5.5 «Zero-alloc» — что реально

План честно формулирует это как цели по путям (§11), а не лозунг. Реалистичность:

```text
запись в IBufferWriter, record из примитивов, без фаз     достижимо, но нужно убрать HashSet циклов и
                                                          MemoryStream AAD (P7)
то же со сжатием/шифрованием                               достижимо с пул-буферами; BrotliEncoder и
                                                          AesGcm могут аллоцировать внутри себя — мерить
чтение: ровно возвращаемый объект                          достижимо для record из примитивов
чтение массива: ровно итоговый массив                      достижимо: пул-буфер, потом один массив
холодный старт                                             не ноль и не будет: построение плана типа
строки, коллекции, сам граф                                не ноль по определению
```

Ни одно из этого не станет утверждением в README, пока не измерено (§28 Benchmark-Plan) — и это
правильно.

# 7. Решения D-1…D-10 и риски — что за ними стоит

## 7.1 Решения

**D-1. Сжатие V0 по умолчанию.** План: нет, только явно. *Смысл:* всегда включённое сжатие *увеличивает*
маленькие сообщения (у Brotli/Deflate есть свои служебные байты) и замедляет самый быстрый путь.
*Моё мнение:* рекомендация правильная. Решение имеет смысл только если принят R7 вообще (вопрос 3).

**D-2. Отпечаток схемы.** План: да, опционально, критичный. *Смысл:* позиционная раскладка при
несовпадении типов читает мусор; отпечаток превращает это в понятную ошибку. *Моё мнение:* идея
хорошая, но не для R6 — см. P10, P11. Extensions позволяют добавить её позже без поломок.

**D-3. Битовая маска null.** План: отложить до данных после R6. *Смысл:* объект с 20 nullable-полями
тратит 20 байт на флаги; маска — 3 байта. *Моё мнение:* отложить нельзя — см. P2. Либо решить до R6
(лучше по замеру на текущем коде: `SIZE-05` уже меряет стоимость null), либо сознательно отказаться
для v1.

**D-4. Zstandard и LZ4.** План: отдельные пакеты с нативной зависимостью. *Смысл:* ядро без нативных
зависимостей — это правильно, их трудно поставлять на все платформы. *Моё мнение:* согласен, плюс см.
P13 про .NET 11. Это можно решать после v1.0 — пакеты аддитивны, если `ICompressionAlgorithm`
финализирован.

**D-5. Асинхронность.** План: только на границе кадра. *Смысл:* движок не `await`-ит; асинхронно только
«дождаться, пока придёт целый кадр», дальше синхронный разбор. Так делают зрелые сериализаторы, и
это сохраняет глубину/бюджеты как есть. *Цена:* весь кадр в памяти (как и сегодня в V1). *Моё
мнение:* правильно.

**D-6. `StreamExtensions` — 12 перегрузок.** План: одна фабрика `BinarySerializerOptions.FromPayload`.
*Смысл:* удобство «прочитай заголовок и настрой себя сам». *Моё мнение:* упрощение правильное; но это
удаление публичной поверхности — решать до релиза.

**D-7. Публиковать `ITypeFormatter`.** План: не в v1.0. *Моё мнение:* согласен — публикация заморозит
протокол обхода, а он как раз переделывается.

**D-8. Populate-in-place.** План: по одному входу на тип источника, только member-encoded типы. *Смысл:*
«прочитай в существующий объект» размножается на каждый новый тип источника. *Моё мнение:* разумно.

**D-9. Номер версии нового V1.** План: оставить 1. *Смысл:* никто не видел старого V1, различать
нечего. *Моё мнение:* правильно — при условии, что в релиз не уйдёт ни одного payload старого вида.

**D-10. Метка релиза генератора.** Технически хватит минорной, если генератор не меняет ни байта и ни
сигнатуры. Это продуктовое решение, не техническое.

## 7.2 Риски — что они значат

| Риск из плана | Что это значит на деле |
|---|---|
| Типизированный движок стоит больше холодного старта, чем экономит | Каждое generic-закрытие над value-типом JIT компилирует отдельно; первый `Serialize` нового типа станет медленнее. Для сервиса это не важно, для CLI/функций — важно |
| Типизированная форма тихо заберёт цикл у движка | Самый опасный: так возвращается «безопасность по соглашению». Защита — тесты INV-5 в том же этапе |
| Внутренние этапы незаметно меняют поведение | Защищают фикстуры и оракул; работает, пока провод не трогают |
| Исключение для фикстур станет привычкой | Защищает запись в `CLAUDE.md` |
| Чтение сверх кадра из non-seekable потока | Реальный класс ошибок; тестовый дубль, падающий на лишнем чтении, — правильная защита |
| План разойдётся с кодом | Защищает правило «документы — в том же этапе» |
| Релиз уезжает | Ты это принял в брифе; см. §2 — можно не принимать |

**Рисков, которых в плане нет:**

- **Объём.** Фактически это второй движок до первого релиза: 8,9 тыс. строк `src/` и 1 659 тестов,
  которые переписываются под новые типы. Риск не в ошибке, а в том, что релиз не наступит.
- **Потеря понимания.** Ты сам написал, что проект уходит из рук. Каждый этап R1–R8 добавляет кода,
  который ты не писал. Порядок «сначала внешнее» оставляет тебе время разобраться в замороженной части
  до того, как меняется нутро.
- **`ref struct` меняет форму движка целиком** (§4.5) — больше работы, чем выглядит в одной строке R4.
